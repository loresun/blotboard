# 部署、更新与源码发布

## 支持范围

Blotboard 面向单用户、单进程、本地磁盘的数据管理。可用于团队内部受信任环境；它没有账号隔离、角色权限、租户边界、审计防篡改或高可用承诺。商业使用许可见 LICENSE；不要把许可等同于公网多租户服务的验收。

默认绑定 `127.0.0.1`。要在局域网共享，管理员显式设置 `BLOTBOARD_HOST=0.0.0.0`，并对能访问该网络的人承担信任。公网入口必须在反向代理做身份鉴权，回源保持 loopback；详见 [安全说明](../SECURITY.md)。

## 第一次启动

用可信源码目录执行 `npm ci`、`npm run build`、`npm start`。不要与其他实例共用用户数据目录。未配置外部集成时使用内置 local 任务后端，知识库和图书来源入口隐藏，数据不会自动送往作者的服务。

## 更新正在运行的服务

1. 在独立工作区安装依赖、修改代码、运行 `npm run check`，避免测试构建碰到正在提供服务的 `.next`。
2. 停止要更新的 Blotboard。对 PM2 使用 `pm2 stop blotboard`，不要停止其他项目。
3. 备份用户数据目录（包含 boards、uploads、issues、runner-settings、runs、checkpoints）。备份留在发布目录外，妥善保管其中的凭证。只有服务停写后，这份备份才有一致性保证。
4. 在目标工作区更新代码，执行 `npm ci`、`npm run build`。失败就保持停机，恢复先前源码和构建；不要继续启动半成品。
5. 构建成功后 `pm2 restart blotboard`，或用原启动方式启动。保留该部署自己的环境变量与数据目录。
6. 执行 `npm run doctor`，确认首页引用的 JS/CSS 全部成功且 MIME 正确；再用浏览器打开已有画板验证。

生产进程启动时登记工作区锁，`npm run build` 检测到同一工作区仍在服务时会拒绝覆盖。构建中启动服务也会被拒绝。锁在 `.blotboard-runtime/`，只存 PID，不是用户数据；每次预留使用唯一文件名，正常退出自动释放；异常退出的死进程标记会被忽略而不被自动删除，避免清理旧锁时误删其他进程的新锁。损坏或尚未写完的协调文件会拒绝继续，确认无构建/服务后再清理。该机制保护本项目入口，不应绕开它去手动删除/替换 `.next`。升级前启动的老进程尚无锁，第一次升级仍必须先停止。开发模式使用 Next 独立的 dev 产物，生产检查请始终在独立工作区执行。

`health` 返回 200 只代表 API 活着。旧进程持有旧资源映射而磁盘已是新构建时，会出现首页 200、JS/CSS 500、MIME 错误与 ChunkLoadError；`doctor` 会额外检查这些资源。

## 对外发布源码

先完成 `npm run check`，精确提交本项目源码，使工作区干净，再执行 `npm run release:source`。输出当前提交的压缩源码包与 SHA-256，**不携带 `.git` 历史**。发布门禁仅允许项目源码、文档、模板和规格，拒绝个人配置、用户画板、附件、迁移备份、构建缓存与符号链接。

旧 Git 历史可能含历史私人地址，即使当前文件已经清理也不能直接公开。第一次开源从审核后的源码包建立新仓库；该工具不自动修改历史、不推送远端、不发布 npm。

目前根包保留 `private: true`，npm 占位目录不代表可用安装包。MCP 使用本地源码 `npm link` 后的 `blotboard mcp`，或在 MCP 配置中指定 Node 与可信源码目录中的 CLI。未来正式发包必须另行验证包名归属、包内容、安装流程与版本。

## 回滚演练

在单独的数据副本与独立端口恢复备份，启动旧版本，验证板数、附件与关键工作流。确认恢复可用后再切换真实服务。不要让新旧两个进程同时写同一数据目录。
